# Stage 4 conversation upgrade: first implementation slice

Implemented 2026-11-19. This is a deterministic conversation layer, not the planned general LLM interpreter.

## Implemented
- The live /api/chat endpoint now uses backend/conversation_service.py over existing guarded chat tools.
- Session context stores the last discussed food, pending food clarification and at most 40 question/answer turns.
- Food references are valid only for the same accepted plan version; stale references require clarification.
- Nutrient answers distinguish daily basket, named food, meal and one catalog serving. Multiple named nutrients are supported. Missing nutrient values produce known-subtotal wording.
- Explicit replacements carry both the excluded food and an exact replacement serving quantity into the existing solver and independent validator. Missing quantities and ambiguous foods prompt clarification.
- Negative mutation requests are stopped for clarification. Medical, allergy, protected-rule, screening and version requests continue through existing guards.
- Frontend shows clarification choices; only the latest turn's choices are enabled.

## Verification
19 tests passed: eight new synthetic conversation tests plus 11 existing chat repair tests. Covered food arithmetic, one-serving scope, follow-up resolution, clarification completion, meal/multiple-nutrient scope, exact replacement tool arguments, negation, stale context and allergy persistence. Temporary synthetic sessions only. npm run build passed TypeScript and Vite compilation. No browser interaction or real LLM benchmark was run.

## Remaining work
1. Schema-constrained LLM interpretation with explicit ambiguity and negation handling, validated against current catalog and session state; measure GPU latency before enabling by default.
2. General compound actions, alternate units, exact meal changes and richer clarification state (this slice supports food-choice clarification only).
3. Grounded education and explanations with curated sources; current answers remain backend-produced.
4. Conversation restore UI, source display, proposal rejection/modification and clearer version indicators.
5. Broader paraphrase, multi-turn and adversarial evaluation. The historical 76/78 benchmark applies to the previous measured source snapshot, not this new layer.

## Limits
The transcript is not currently passed to an LLM. Context resolves food references, not arbitrary dialogue. Meal quantities are read from the existing deterministic schedule. Exact replacement quantities refer to whole catalog servings; gram conversions need further implementation. Compound replacement constraints are clarified instead of partially applied. Other legacy intent handlers retain their existing limitations. Existing plan-session storage remains local JSON and requires further concurrency/session-access work before multi-user deployment. Backend restart is needed to load changed Python code.


## Natural-language interpreter implementation — 2026-11-19

Added backend/chat_interpreter.py: local Qwen JSON interpretation, strict Pydantic field validation, current-plan/catalog ID checks, nutrient allowlist, serving bounds and cross-field consistency checks. Unsupported or ambiguous requests ask for clarification. Read requests are converted to backend queries; interpreted remove/replace requests require an explicit confirmation before invoking the existing solver. Final proposed plans still require acceptance. Same-version context and the last four same-version conversation turns are supplied. Model output is never executed as code or displayed as factual prose.

The API has a separate use_llm_interpretation flag. Frontend exposes an experimental natural-wording checkbox (off by default), interpreted-request text and visible fallback status. The existing use_llm_explanation flag remains distinct. Interpreter calls serialize within this interpreter; unavailable CUDA, busy interpreter, invalid JSON or rejected schema falls back to the standard assistant. Generation is capped at 220 tokens; model loading/generation has no enforced wall-clock cancellation in the existing shared backend. Concurrent compiler/intake model access still needs coordination for multi-user deployment.

Validation: 25 tests passed (six interpreter tests with mocked generation, eight conversation tests and 11 existing chat repair tests). Frontend TypeScript/Vite build passed. No actual Qwen calls have been made for this new interpreter. pilot_stage4_interpreter_v2.py prepares six synthetic requests using real catalog names; --run performs and journals the GPU calls. Pilot is awaiting the user's independent-run approval. This is not a full conversational accuracy benchmark.

Still pending: measured GPU interpretation quality/latency, broader compound-intent support, semantic evaluation, general nutrition retrieval, grounded explanations, and conversation restoration UI. Existing historical Stage 4 benchmark figures do not validate this implementation.

STAGE 4 REPLACEMENT WORDING AND FOLLOW-UPS — 2026-11-19
Added explicit replacement normalization for “I would rather have … instead of …”, “I'd rather have …”, “Could/Can I have … in place of …”, and “Please use … instead of …”. A trailing comma plus explicit serving count is retained. These recognized forms bypass the LLM and preserve source, replacement and whole-serving quantity. The previously failed hybrid-pilot wording is now covered by a deterministic regression test; this does not retrospectively change that pilot's 7/8 result.

Quantity context is bound to the accepted plan version and cleared by unrelated intervening messages. Food clarification context is also consumed instead of indefinitely lingering. Extra meal restrictions, extra sentences and weight/volume units prompt clarification rather than being silently discarded by the replacement parser.
